# Development container

This folder defines the project's **devcontainer**: a Docker container that
VS Code opens the project in. All tools the project needs are installed in the
container, so your machine only needs Docker and VS Code, and everyone works in
the same environment.

## What's inside

- **Image:** `mcr.microsoft.com/devcontainers/python:3.14-bookworm`, timezone `Europe/Bratislava`.
- **Tools:** [uv](https://docs.astral.sh/uv/) 0.12.19 (pinned) for Python,
  dependencies and tools (Ruff, ty, pytest run through `uv run`).
  `UV_LINK_MODE=copy`, because `.venv` lives on the bind mount.
- **On create:** marks the workspace as a git `safe.directory`, then runs
  `uv sync` in `animanga/` to create `animanga/.venv`.
- **VS Code:** Python interpreter set to `animanga/.venv` (the ty extension: `.vscode/settings.json`), pytest runs
  `animanga/tests`, crawled data folders are excluded from file watching and
  search. Extensions: Python, Pylance, Ruff, ty, debugger and autoDocstring.
- **Process init:** `init: true` in compose, so exited background processes
  (crawlers) don't pile up as zombies.
- **Workspace:** `/workspace/vinf`.
- **Docker inside the container:** `docker` and `docker compose` work and use your machine's Docker (`docker-outside-of-docker`). `HOST_WORKSPACE_FOLDER` holds the project's path on your machine, which bind mounts in those commands need.

## Getting started

1. Install [Docker](https://docs.docker.com/get-docker/) and
   [VS Code](https://code.visualstudio.com/) with the
   [Dev Containers](https://marketplace.visualstudio.com/items?itemName=ms-vscode-remote.remote-containers)
   extension.
2. Open the project folder in VS Code and run **Dev Containers: Reopen in
   Container** (command palette). The first build takes a few minutes.
3. After changing a file in this folder, run **Dev Containers: Rebuild
   Container**.

## Files

| File | Purpose |
| --- | --- |
| `devcontainer.json` | VS Code settings for the container: compose service, workspace folder, features, extensions |
| `docker-compose-dev.yml` | the dev service: build, workspace mount, `init: true` |
| `Dockerfile` | the image: base image and installed tools |
| `devcontainer-lock.json` | pinned versions of the features (generated by VS Code) |

## Your own extensions

`devcontainer.json` lists only the language support the project needs. Add
the extensions you like (git tools, spell-check, AI assistants, …) for
yourself in your VS Code **user** settings, and they are installed in every
devcontainer you open:

```json
"dev.containers.defaultExtensions": [
    "eamodio.gitlens"
]
```

## Mounting your own folders

Mounts you need only for yourself (your tool config, data stored elsewhere on
your disk, …) don't belong in this folder: everything here applies to everyone.
Add them without changing the project, through a personal
[Dev Container feature](https://containers.dev/implementors/features/):

1. Create a feature whose `devcontainer-feature.json` declares the mounts:

   ```json
   {
       "id": "my-mounts",
       "version": "1.0.0",
       "name": "My mounts",
       "mounts": [
           {
               "type": "bind",
               "source": "${localEnv:HOME}/<folder>",
               "target": "/home/vscode/<folder>"
           }
       ]
   }
   ```

   A feature also needs an `install.sh`; for mounts only it can just `echo`.
2. Publish it, e.g. to GitHub's registry (ghcr.io) with the
   [feature starter](https://github.com/devcontainers/feature-starter) workflow.
3. Add it to your VS Code **user** settings:

   ```json
   "dev.containers.defaultFeatures": {
       "ghcr.io/<you>/<repo>/my-mounts:1": {}
   }
   ```

4. Rebuild the container.

VS Code adds the feature to every devcontainer you open; the project's files
stay unchanged. The source folder must exist on your machine, and `target`
can't use `~`, so write the container user's home (`/home/vscode`).
